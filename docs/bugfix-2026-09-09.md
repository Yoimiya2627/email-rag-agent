# 2026-09-09 BUG 修复与兼容说明

本轮修复依据 Astra 交叉审查的确定问题。未安装依赖、下载模型、连接真实邮箱或运行云端评测。架构调整建议单独交付，未据此引入新的服务架构。

## 行为变化

- MCP 工具的返回签名现在与统一结果对象一致；`search_emails` 的 `labels=null`、`limit=null` 明确使用默认值。实际 SDK 的六种工具调用有进程内回归。
- 工具结果超限时保留可读文本前缀和原始 ID，避免 body/chunks 重复。`truncated` 表示内容不完整；`sources` 是累计检索候选，`metadata.model_visible_evidence` 是模型实际看到的来源 ID，二者不能混用。引用检查仍只验证 ID，不验证事实是否被原文支持。
- Gmail 同步以实际 corpus 为准去重；同目录临时文件、flush/fsync 和原子替换保护已有 JSON。corpus 先于 state 持久化。并发同步由 output/state 的 SQLite sidecar 锁串行化，请保留 `.sync-lock.sqlite3` 文件。
- 同步恢复仍受当前 query/max-results 限制，不代表自动找回查询范围之外的全部历史邮件；已有邮件的标签、删除等增量更新尚未实现。
- 邮件清洗明确区分 `body_format=plain/html`；详见 [入库保真说明](ingestion_fidelity.md)。普通致谢词不再触发正文删除，仅正文后的明确 `-- ` 独行作为签名分隔符。HTML 隐式关闭 head、附件与正文分离、字符实体和短尾切分均补了回归。
- 新索引记录清洗后文本的 offsets/hash。`reconstruction_exact` 只证明索引文本按区间完整重建，不能证明与原始 MIME 字节一致。旧索引没有这些信息时不会猜测去重。
- 所有消费会话历史的主生成路径共用预算裁剪，优先保留较新完整轮次。当前请求或证据本身仍放不下时，普通 API 返回 413；Agent 模式保留结构化预算状态。存储中的对话不因提示词裁剪而被删除。
- 两个 CLI 导入先严格预检整批数据，坏 JSON、空列表、无效记录或重复 ID 直接拒绝，不再跳过坏记录后执行替换。`--clear` / `--clear-index` 在全部 embedding 和 upsert 成功后才删除遗漏旧 chunks。Chroma 并不提供这里需要的整批事务回滚；upsert 中途失败仍可能留下部分覆盖。
- LLM 重排分数在排序前校验为有限的 0–10 整数值；CrossEncoder 只要求有限数值，保留合法负 logits。非法结果进入既有降级路径。
- RAGAS-style 三项评分只接受 0–1 有限数值；错误类型/越界触发重试与明确降级。每题增加 `scoring_method/scoring_status`，汇总增加 `scoring.method_counts/averages_by_method`。`embedding_proxy` 是相似度代理，不能当作 LLM 事实性评分。总平均仍计入失败题零分，分组均值与失败数另列。
- Agent 评测 provenance 使用 `fingerprint_format=text-lf-v1`，对源码和题集的换行做规范化。LF/CRLF checkout 不应再造成误判；代码或题集内容变化仍会被发现。当前版本校验要求新的 fingerprint_format。

## 回到真实环境后的迁移

1. 先保存可靠原始邮件 JSON。旧 HTML JSON 必须显式标记 `body_format: "html"`；不做字符串猜测。Gmail 转换器输出已解码的 plain 内容，无需二次解码。
2. 从可靠原始语料重新索引。旧 cleaner 已经删除的正文无法从残缺 chunks 恢复。自定义 JSON 若含无效或重复记录，应先修正后导入。
3. 重新生成评测结果。仓库历史指标保留作历史参考，不能视作此次修改后的验证结果；不要手改旧报告的 provenance 冒充重跑。
4. 在原有环境执行 `python -m pytest tests/ -q`，然后分别验证真实 Chroma/embedding、Gmail 只读同步、MCP transport、模型与 SSE。离线测试只证明已覆盖的业务契约与故障分支，不代表真实邮箱端到端成功。
