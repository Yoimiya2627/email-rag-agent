## Gmail 升级步骤与兼容变化

1. 停止正在执行的任务，备份现有审批数据库和凭据。`unknown` 或 `executing` 审批先按原流程核对远端结果，不能通过换版本重试。
2. 在自己的目标机器、确认配置对应邮箱后，显式执行：

   ```powershell
   .\.venv\Scripts\python.exe -m agents.mail_providers authorize
   ```

   该命令可能打开授权浏览器或刷新已有 token；随后用 Gmail `getProfile` 核验实际账号，再原子写入 `_email_agent_binding`。现有 `gmail.compose` scope 支持该只读身份核验，依据 [Google getProfile 文档](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users/getProfile)。授权命令本身不创建或发送草稿。

3. 每次显式授权都会生成新授权版本，即使 token 尚未过期。token 文件内容变化（包括刷新）、scope、userId 或 provider 改变，均使之前的待审批绑定失效。先完成授权，再生成和审核新的待审批单。
4. 旧 Gmail 待审批单缺少绑定，执行时会以执行前条件失败拒绝，须重新创建；旧模拟审批仍可模拟执行。已完成动作保留原结果，不会再次创建草稿。已绑定的 Gmail 审批也不能通过切换配置变成模拟动作。
5. 审批按钮仍只创建 Gmail 草稿。创建待审批单仅读取本地绑定，不打开 OAuth、不刷新 token；执行前读远端账号，只有核验一致才提交草稿。提交后超时仍为结果未知，需人工核对。

绑定由服务端写入现有审批 payload，并纳入原有内容摘要；没有数据库 schema 迁移。评测作用域始终使用模拟绑定，日常配置为 Gmail 时也不读取日常凭据。

## 原件重放与旧档案

每个原始根文件对应 `raw/selections/<根文件名>.json`。描述文件记录根原件摘要、选定 `versions/...json` 的相对路径及摘要、邮件 ID。完整版本保持原有不可变存档方式；选择记录通过原子替换更新。选择记录落盘失败时同步中止并保留待处理状态。

- 新档案默认读取选择记录。路径越界、链接/重解析点、原件被修改、版本丢失或身份不符均停止该条解析，不能靠已有 checkpoint 绕过原件校验。
- 旧档案没有选择记录且根原件缺少外部正文时，按完整邮件对象匹配版本。等价内容/账号仅抓取时间不同可以归并；正文或账号存在歧义时报 `ambiguous_capture_versions`，不猜最新文件。
- 若原件从未抓到正文，离线重放不能凭空补回，仍需回家重新只读同步。
- 重放不会覆盖原 corpus；任何一条失败都不发布新的 corpus。默认 dry-run 会写报告，不发布数据文件或新 checkpoint。

在项目根目录，使用备份的原件目录和一个**尚不存在**的输出文件先预览（下面路径需替换成自己的副本路径）：

```powershell
.\.venv\Scripts\python.exe scripts/replay_gmail_captures.py --raw-dir D:/mail-check/captures --output D:/mail-check/replayed.json --original-corpus D:/mail-check/original.json
```

核对生成的 `replayed.json.report.json`：`failed_count=0`，并逐项查看 `capture_file`、`selection_method`、`body_changed`、`numbers_changed`、`negation_changed`。确认后才在相同命令末尾加 `--write`，仍写入新文件；新 corpus 的索引发布另行验收。

出现歧义时，先人工核对版本，再在原件目录以外创建选择记录目录，通过 `--selection-dir D:/mail-check/selections` 指定。显式目录要求每个根文件都有选择记录，缺失即报错。可用 `core.capture_selection.selection_record(raw_dir, root_file, capture_file, message_id)` 生成该结构；所有参数须指向已核对的真实档案，选定版本必须仍在原件目录之内。无需修改原件 JSON。不要只填文件名绕过摘要核验。
