# 2026-09-12 问候路由修复与复审验收

本轮修复用户截图中“只输入你好，却引用三封邮件”的问题，并对相关聊天、会话、任务恢复、证据和审批路径复审。修复仅限有代码证据或可重复验证的问题，没有实施 163 接入或大规模重构。

## 确认并修复的问题

| 问题 | 原因与影响 | 本轮处理及验证 |
| --- | --- | --- |
| 问候被带入邮件问答 | 协调器把 GENERAL 映射到 Retriever；SSE 也让 GENERAL 进入检索，Self-RAG 没有问候分支 | 增加整句问候、致谢、帮助的直接回答；普通、流式、Self-RAG、自主 Agent 四种聊天入口均不为这些消息调用模型或检索。其他 GENERAL 输入请求澄清。混合问候与邮件任务继续走实际任务流程 |
| 截断或仅含推理的模型输出可被误用 | 意图分类、Self-RAG 评分曾从 reasoning_content 解析结果；改写和评分未一致检查完成状态 | 仅接受完成的最终内容。无效意图转澄清，无效改写保留原查询，无效评分拒绝该批未核验候选。截断、仅推理、空结果和正常结果均有回归 |
| 纯空白请求可进入执行 | 只有字符串长度检查，空格、制表符等仍合法 | AgentRequest 与 QueryRequest 共用非空白校验，返回 422；合法输入保留原文。自动测试验证在模型、检索和入队之前拦截，实际六个入口也均返回 422 |
| 上下文初始化失败后又触发二次异常 | 异常收尾直接调用空 task_context 的 items()，掩盖原始错误 | 收尾允许空上下文；故障注入验证普通聊天保留 504，SSE 输出原始超时错误，失败记录不进入有效历史上下文 |
| 后台任务完成记录存在两次写入的故障窗口 | 已写入对话后，单独保存完成 checkpoint 失败，会留下可恢复的旧规划；复现中恢复后模型调用和历史记录均由一次变成两次 | 成功状态、结果、完成 checkpoint 改为同一 SQL 更新。验证单独 checkpoint 写故障不再阻碍完成，完成状态一致、失败回滚、一次模型调用及一条历史记录 |

问候快捷分支只匹配完整输入，不按“你好”前缀截断任务；保留身份、取消、截止时间和恢复检查。页面意图标签由“问答”改为“对话 / 需求澄清”。Self-RAG 的普通邮件请求新增一次意图判断，可能略增延迟及模型用量；问候直接返回。
