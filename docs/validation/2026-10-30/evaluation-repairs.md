# Agent 评测修复与当前验收状态

2026-10-30。PR #1 保持开放，未合入 main。按项目所有者要求，本阶段完成代码与离线检查，真实模型评测稍后再运行。

## 本轮修复

1. 评测的每个任务建立独立会话，接入应用已有的会话仓库和工具结果存储，使旧工具结果可以压缩；审批与上下文状态都限制在评测目录，任务间不能互读工具结果。
2. 评分使用实际可见来源对应的证据，保留正文、业务信息、覆盖范围和可见区间，去除重复哈希等记录字段。未展示的检索候选不再全部塞给评分模型；输入过大仍明确失败，不静默裁剪正文。逐题报告记录评分输入、错误原因及模型用量。
3. 评分调用应用相同的 DeepSeek thinking 配置，保留超时、零重试、完整输出及严格整数 0/1 检查。规划模型默认跟随已配置的生成模型，避免默认指向旧名称。
4. 明确可修改回复文本与外部邮箱草稿的区别；允许用户已授权“找一封”时选择相关候选并完成草稿。发送仍经过原有人工审批。
5. 引用检查不再丢掉原执行退出原因。达到步数上限后即使还存在引用错误，步数上限指标仍会记录为真。
6. 新增 `--reference-date`，仅对可信评测作用域中的相对日期解释生效；检索、统计、规划提示和评分共用日期。正常应用仍使用实际日期，审批过期时间及运行超时不受影响。
7. 完成一题即保存诊断记录；遇到 HTTP 401/402/403/404 等账户或配置错误停止批次并返回非零退出码。未执行题目不生成评分；未完成批次不能靠已完成子集通过质量门槛。

固定题目、邮件内容及 80% 等门槛没有修改。报告中的预期工具覆盖率仍不等同于所有工具调用都正确。

- GitHub 的 Ubuntu core、Ubuntu storage、Windows core 三组完整回归状态见 [PR #1](https://github.com/Yoimiya2627/email-rag-agent/pull/1)。
- 单题诊断确认工具结果存储和压缩实际生效：存储 6 个结果、压缩 4 个旧结果；该题仍未成功，因此不将此诊断描述为质量达标。
- 重跑期间，2026-10-30 11:49:02 至 11:50:52（本机日志时间）记录了 96 次 HTTP 402。该批次在增加立即停止逻辑之前运行，共 105 条记录，仅 9 条完成评分，96 条为接口错误、未评分。不能将其总分解释为修复后的模型质量，也不能把 9 题子集当作完整评测。
- HTTP 402 的含义见 [DeepSeek 官方错误码说明](https://api-docs.deepseek.com/quick_start/error_codes/)；接口错误批次单独保留，没有替换历史基线或伪造通过结果。
- 最新源码尚无有效的完整真实评测报告，因此质量门槛仍未验收。仓库现有 `agent_eval.json` 是历史基线，源码指纹检查会识别其过期。

## 日期基准与题库问题

合成语料日期范围为 2026-01-01 至 2026-04-28。项目所有者已确认后续以 **2026-04-28** 为固定检索参考日期，便于重复评测。

仍需独立审查题库：例如有的题目只要求解释安全工具，却强制要求调用统计或搜索；首题的“Q3 预算评审会议”未在语料中找到相符的主题，正文同时含 Q3 与预算的两封邮件分别讨论 Q2 基础设施预算和服务器采购。不能为了满足此类预期而捏造邮件或执行无关工具。本轮未改写这些题目或判定条件。

## 后续复跑

使用已准备好的独立合成语料索引、模拟邮件 provider 和独立状态目录。恢复模型服务后，在可用环境执行：

```bash
python scripts/run_agent_eval.py --reference-date 2026-04-28 --run-dir <新的评测目录> --output <新的报告.json> --report-output <新的报告.md>
python scripts/check_agent_eval_gate.py --input <新的报告.json>
```

不复用旧分数，不删除失败题，不把调用完成视为质量通过；新报告完成并审查后再更新仓库基线。PR 合并仍需后续决定。
