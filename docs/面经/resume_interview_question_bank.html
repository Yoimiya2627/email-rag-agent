1. 项目整体讲解

30 秒版本：这是一个智能邮件 RAG Agent 系统。底层用向量检索 + BM25 + RRF 做混合检索，支持邮件问答；上层基于 DeepSeek function calling 实现 ReAct 式 agent loop，把检索、取详情、摘要、起草回信、申请发信、统计分析封装成 6 个工具。最新一版又把工具层升级为 MCP-ready：同一份 tool_registry.py 同时派生本地 function schema 和 FastMCP tools/resources/prompts，并补了 bearer token、tool policy、audit query、人审审批和 EvalOps trace。项目还做了 RAGAS-style 6 版消融、54 条 Agent 任务评测、118 个 pytest 用例和失败模式护栏。

3 分钟版本：系统入口是 Streamlit 前端，后端是 FastAPI。普通模式走 /chat，Coordinator 先做 LLM 意图分类，再路由到 RetrieverAgent、SummarizerAgent、WriterAgent、AnalyzerAgent。流式模式走 /chat/stream，用 worker 线程和 asyncio.Queue 桥接同步 LLM 流和异步 SSE。Self-RAG 走 /chat/graph，用 LangGraph 做检索后自检和 rewrite。Agent 模式走 /chat/agent，planner 模型拿到 6 个工具 schema 后，根据任务自主调用工具，并把工具结果回灌给模型继续判断下一步；工具后端默认 local，也可以通过 AGENT_TOOL_BACKEND=mcp 切到 MCP backend，经 tools/list 动态发现、tools/call 执行。高风险 send_email 不直接发信，只创建 pending approval，由人工 approve/reject。

面试时的核心定位：不要把项目讲成“我调了 DeepSeek API”。要讲成“我把 RAG 能力工具化，用 function calling 做 Agent 编排，并把工具层升级成 MCP-ready 的标准化接入层，同时补了高风险动作人审、MCP 权限审计和 EvalOps 可观测”。
三份文档怎么配合：这份 HTML 是“广度题库”，负责把面试官可能问到的问题铺开；interview_qa_walkthrough_v2_full.html 是“深度讲稿”，负责把 6 张王炸牌讲透；code_walkthrough_private.html 是“代码速查”，负责把每个关键文件讲清。三份按这个顺序消化，就等于把项目从简历、架构、代码、评测、追问都过了一遍。

4. 必须会的项目题

Q1：请你用一分钟介绍这个项目。

我做的是一个智能邮件 RAG Agent 系统。底层是邮件 RAG，用向量检索、BM25 和 RRF 融合做邮件问答；上层新增了基于 DeepSeek function calling 的 ReAct 式 agent loop，把检索、取详情、摘要、起草回复、申请发信、统计封装为 6 个工具，让模型可以自主完成多步任务。最新一版把工具层升级为 MCP-ready：同一份 tool_registry.py 既派生本地 function schema，也通过 FastMCP 暴露 tools/resources/prompts，并补了 token、tool policy、audit query、approval 和 trace/EvalOps。系统提供普通 RAG、Self-RAG 和 Function-calling Agent 三条链路，同时有 6 版检索消融、54 条 Agent 任务评测和 118 个 pytest 用例。

追问重点：面试官想确认你不是只会“调 API”，而是能讲清架构、链路、评测和工程兜底。
Q2：这个项目为什么叫 Agent，不只是 RAG？

普通 RAG 是 query -> retrieve -> generate，核心是查资料后回答。我的 /chat/agent 是 plan -> tool call -> observe -> re-plan，模型根据任务自主选择工具。比如“找一封报销邮件并帮我回复”，它会先调用 search_emails，拿到 email_id 后调用 get_email，最后调用 draft_reply。所以 RAG 是底层能力，Agent 是任务编排层。

Q3：当前 Coordinator 还在吗？和 Agent loop 是什么关系？

还在。/chat 和 /chat/stream 仍然走 Coordinator，由 LLM 做一次意图分类，然后路由到 RetrieverAgent、SummarizerAgent、WriterAgent、AnalyzerAgent。/chat/agent 是新增链路，不做固定意图路由，而是让 planner 模型根据工具 schema 多轮调用工具。Coordinator 是稳定单步链路，Agent loop 是自主多步链路。

Q4：三条聊天链路分别适合什么场景？
链路端点特点适合场景

Q5：你作为项目负责人，这次架构升级的核心是什么？

核心是八件事。第一，把原来的 RAG 和 Specialist Agent 能力工具化，新增 function-calling agent loop。第二，把工具定义抽成 tool_registry.py，同一份定义派生本地 schema 和 FastMCP 注册，避免工具定义漂移。第三，给 MCP backend 补 token、schema cache 和 audit。第四，用 tool_policy.py 做 allowed-tools/read-only 可见性控制。第五，把高风险 send_email 设计成人审 pending approval。第六，用 agent trace 记录 tool call、状态和耗时。第七，用 EvalOps 做 54 条任务集、failure_category 和报告。第八，把标准 RAG 链路抽到 core.pipeline.retrieve()，让产品和评测尽量复用同一条检索管线。

边界要说清：/chat/graph 和 /chat/agent 不是完整调用 retrieve()，它们复用的是底层检索、后过滤和 rerank 组件。
Q6：如果面试官追问“你这里到底是不是 Multi-Agent”，怎么解释？

新版简历已经把项目名收敛成“智能邮件 Agent 系统”，不再靠 Multi-Agent 这个词硬撑。但如果被问到，要解释清楚：传统 /chat 链路里有 RetrieverAgent、SummarizerAgent、WriterAgent、AnalyzerAgent 这些专职 Agent，由 Coordinator 路由；新版 /chat/agent 则是 function-calling Agent，把这些能力进一步工具化。不能说它是很多完全自治 Agent 协作的复杂系统，更准确的说法是“邮件 RAG 底座 + 专职 Agent 路由 + function-calling 工具编排”。

5. Agent / Function Calling / MCP 高频题

Q7：function-calling agent loop 具体流程是什么？

代码在 agents/agent_loop.py。流程是：构造 system message 和历史 memory，把用户 query 发给 planner 模型，同时传入工具 schema。schema 默认由 local backend 从 tool_registry.py 派生；切到 MCP backend 时，由 mcp_adapter.py 通过 tools/list 转成 planner 能用的 function schema。如果模型返回 tool_calls，后端解析函数名和 JSON 参数，调用本地工具或通过 tools/call 调 MCP server。工具结果会以 role=tool 的消息回灌给模型。高风险 send_email 只返回 pending approval。trace 会记录每一步工具调用和耗时。没有 tool call 时，message.content 就是最终答案。

Q8：6 个工具的设计依据是什么？

工具是按邮件系统的高频任务拆出来的：查找邮件用 search_emails，信息不足时用 get_email 取完整内容，多封邮件主题归纳用 summarize_emails，回复场景用 draft_reply，真正发信前用 send_email 创建人审审批单，数据分析用 email_stats。最新版本把这些工具收敛到 tool_registry.py，本地 function calling 和 MCP server 都从 registry 派生，避免同一个工具在两处维护两份 schema。

Q9：tool schema 里最重要的字段是什么？

schema 可以理解成“工具说明书 + 参数合同”。最重要的是工具名、description、parameters、required。description 决定模型什么时候选这个工具，parameters 决定模型如何构造参数，required 决定最小可执行参数。例如 search_emails 必须有 query，get_email 必须有 email_id，draft_reply 必须有 instruction，并可选 email_id 精确回复。

面试时别把它说成数据库 schema。这里的 schema 是给模型看的 JSON 参数规范，作用是减少“模型乱猜工具参数”。
Q10：工具结果怎么跨工具传递？

search_emails 返回结构化结果，包括 email_id、subject、sender、date、snippet、score。这些结果作为 tool message 回灌给模型，模型在下一轮可以把 email_id 作为参数传给 get_email 或 draft_reply。这就是 search -> get_email -> draft_reply 的数据链。

Q11：怎么处理模型生成坏 JSON 或乱传参数？

坏 JSON 在 agent_loop.py 里捕获，解析失败就降级为空参数，让工具层返回明确错误。乱传参数在 call_tool() 中处理：通过 inspect.signature 获取函数签名，丢弃未知 kwarg，检查必填参数是否缺失。如果缺参数或工具异常，返回 {"error": ...}，而不是让整个请求 500。

Q12：怎么避免 Agent 死循环？

两层保护。第一是全局 AGENT_MAX_STEPS，超过最大步数后强制让模型基于已有信息给最终答案。第二是同工具同参数重复检测，用 Counter 统计 (tool, args)，超过 AGENT_MAX_REPEAT 就返回错误提示，要求模型不要继续重复调用。

Q13：为什么不用 LangChain Agent？

这个项目重点是理解和掌控 Agent loop 本身，所以我直接使用 DeepSeek 原生 function calling。这样可以清楚控制工具 schema、消息协议、tool result 回灌、max steps、重复调用检测和测试。LangChain Agent 更适合快速搭建，但抽象层更厚，面试和排查时不容易解释每一步。

Q14：为什么 planner 模型用 deepseek-chat？

function calling 需要模型稳定返回 tool_calls。普通生成链路可以用其他模型，但 agent planner 需要在多轮消息里保持工具调用协议一致。为了降低协议复杂度，/chat/agent 的规划和最终回答都用 AGENT_PLANNER_MODEL=deepseek-chat。

Q15：Agent eval 的 tool_accuracy 怎么理解？

当前实现是 expected tools 是否都出现在 actual tools 里。比如任务期望 search_emails 和 draft_reply，实际调用了 search_emails -> get_email -> draft_reply，仍然算正确，因为 get_email 是合理的中间步骤。这个指标看的是关键工具是否覆盖，不是要求调用序列完全一样。

6. RAG / 检索 / 评测题

Q16：为什么用向量检索 + BM25？

向量检索擅长语义相似，比如“报销”能找到“差旅费用审批”。BM25 擅长关键词精确匹配，比如人名、项目名、PR 编号、金额。邮件场景同时有语义问题和精确实体，所以用混合检索更稳。

Q17：RRF 是什么？为什么不用分数加权？

RRF 是 Reciprocal Rank Fusion，用排名融合不同检索通道。向量相似度通常是 0 到 1，BM25 分数可能是几十，直接加权会量纲冲突。比如 0.7 * cosine 最大也就 0.7，但 0.3 * BM25 如果 BM25=50 就是 15，BM25 会完全压制向量。RRF 不看原始分数，只看 rank：score += weight / (k + rank)，项目里 k=60，向量权重 0.7、BM25 权重 0.3。这样以后加 SPLADE、ColBERT 等新检索路，也可以按排名融合，不用重新对齐分数量纲。

Q18：Reranker 为什么不默认开？

Reranker 有收益但也有成本。V2 到 V3 后，context precision 从 0.5713 升到 0.7147，说明更会筛上下文。但 relevancy 从 0.9567 降到 0.9333，而且多一次 LLM 调用，延迟增加。所以它适合高精度场景，不一定适合作为默认链路。

Q19：为什么默认选 V2？

因为 V2 是业务综合最划算，不是单项指标冠军。当前消融里 V6 的 relevancy 最高 0.9600，V1 的 faithfulness 最高 0.9233，V3 的 context precision 最高 0.7147。V2 的 relevancy 是 0.9567，接近最高 V6，同时 mean 延迟 8.7s、p95 14.4s，不需要额外 reranker/rewrite LLM 调用，所以作为默认方案。

Q20：Query Rewrite 和 Filter extraction 为什么分开？

Query Rewrite 是把口语化问题改成更适合检索的语义查询，比如补全指代词。Filter extraction 是提取结构化条件，比如发件人、日期、标签。前者改变检索 query，后者约束候选结果。如果混在一起，容易出现 query 被改偏或 filter 误杀结果。

Q21：pipeline drift 是什么？你怎么修？

pipeline drift 是产品链路和评测链路不一致。比如产品实际用了 post-filter，但 RAGAS 评测脚本没用，那么离线分数就不能代表线上效果。项目里把标准 RAG 的 rewrite、filter、hybrid search、post-filter、rerank 收敛到 core.pipeline.retrieve()，让 RetrieverAgent、RAGAS-style 评测、延迟测试尽量复用同一链路。

注意边界：Self-RAG 和 Agent 工具链路复用了底层组件，但没有完整走 retrieve()。所以准确说法是“标准 RAG 链路被统一了”，不是“所有链路都完全统一”。
Q22：RAGAS-style 三个指标怎么解释？

answer relevancy 看回答是否贴合问题；faithfulness 看回答是否忠于上下文，少不少编；context precision 看检索出的上下文是否有效，相关内容排得是否靠前。三者对应用户体验、可信度和检索质量。

Q23：为什么说组件不是越多越好？

因为每个组件都有副作用。Reranker 提高 precision 但增加延迟；rewrite 可能提高相关性，也可能改偏；Self-RAG 能自检，但多次 LLM 调用会慢。消融结果显示没有全场最优，所以工程上要按业务目标选择组合，而不是堆组件。

Q24：BM25 cache 为什么需要锁？

BM25 index 构建需要读取所有 chunks 并分词，成本比较高，所以做了缓存。FastAPI 可能并发处理请求，如果多个请求同时发现 cache 为空，会重复构建甚至状态不一致。因此 core.retriever 用 threading.Lock 保护 BM25 cache 的读写。

7. Python / FastAPI / 异步并发题

Q25：FastAPI 中 async endpoint 里面能不能直接跑阻塞函数？

不能随便直接跑。async endpoint 运行在事件循环里，如果里面执行阻塞 I/O 或长时间 CPU 任务，会阻塞整个 event loop，影响其他请求。项目里的 /chat/stream 用 loop.run_in_executor(None, producer) 把同步生成逻辑丢到 worker 线程，再用 asyncio.Queue 把 token 传回异步 SSE。

Q26：asyncio.Queue 在 SSE 里起什么作用？

它是同步 producer 和异步 event_generator 之间的桥。producer 在线程里读取 LLM token，然后通过 loop.call_soon_threadsafe(queue.put_nowait, token) 安全地把 token 放进事件循环队列。event_generator 在 async 环境中 await queue.get()，拿到 token 后 yield SSE 数据。

Q27：SSE 和 WebSocket 有什么区别？为什么这里用 SSE？

SSE 是服务端到客户端的单向流，基于 HTTP，适合 token 流式输出。WebSocket 是双向长连接，适合实时协作、游戏、IM 等双向频繁通信。这里聊天生成主要是服务端不断推 token 给前端，客户端不需要高频反向发送消息，所以 SSE 简单、够用、部署成本低。

Q28：threading.Lock 和 asyncio.Lock 有什么区别？

threading.Lock 用于多线程之间保护共享变量，会阻塞线程。asyncio.Lock 用于同一个事件循环内的协程同步，需要 await。项目里的 session store、ConversationMemory、BM25 cache 可能被线程访问，所以使用 threading.Lock 更合适。

Q29：GIL 是什么？对这个项目有什么影响？

GIL 是 CPython 的全局解释器锁，同一时刻通常只有一个线程执行 Python 字节码。它限制 CPU 密集型多线程并行，但对 I/O 密集型任务影响较小。这个项目的 LLM 调用、HTTP 流、数据库访问主要是 I/O 密集型，用线程桥接 SSE 是合理的。如果是大量 CPU 计算，应考虑进程池或外部服务。

Q30：Python 的可变默认参数有什么坑？

函数默认参数只在定义时创建一次。如果写 def f(x=[])，多次调用会复用同一个列表，造成状态污染。项目里类似 labels: List[str] = None，然后内部用 labels or []，就是为了避免可变默认参数问题。

Q31：深拷贝和浅拷贝区别是什么？

浅拷贝只复制外层容器，内部对象仍共享；深拷贝会递归复制内部对象。比如 list 里套 dict，浅拷贝后修改内部 dict 会影响原对象。工程中处理消息历史、配置、工具参数时，要注意不要意外共享可变对象。

Q32：装饰器是什么？实际有什么用？

装饰器本质是接收函数并返回新函数的高阶函数。FastAPI 的 @app.post("/chat") 就是把普通函数注册成路由处理函数。常见用途还有日志、鉴权、缓存、重试、计时等。

Q33：生成器和普通函数有什么区别？

普通函数一次性返回结果。生成器使用 yield，可以边生产边消费，保留执行状态。SSE 流式输出就很适合生成器，后端每拿到一个 token 就 yield 一个 SSE event，而不是等完整回答生成后再返回。

Q34：异常处理时为什么不能裸 except 后什么都不做？

裸 except 会吞掉错误，排查困难，也可能掩盖严重问题。项目里会捕获异常，但通常会记录日志，并返回结构化错误或降级结果。比如工具调用失败返回 {"error": ...}，reranker 失败返回原排序，同时增加失败计数。

8. C++ / Socket / Kafka / Protocol Buffer 追问题

Q35：Protocol Buffer 相比 JSON 有什么优势？

Protocol Buffer 是二进制序列化，体积更小，解析速度更快，字段类型明确，适合内部服务通信。JSON 可读性强、调试方便，但字段类型松散、体积更大。简历里邮箱服务模块把交互协议重构为 Protobuf，合理的回答是降低传输体积、提升解析效率、让接口契约更稳定。

Q36：Socket 通信为什么会有粘包和拆包？

TCP 是字节流协议，没有消息边界。发送端一次 write 的数据，接收端可能多次 read 才读完，也可能多条消息合在一次 read 里。解决方法通常是固定长度包头、长度字段、分隔符协议或 Protobuf 前加 length-prefix。

Q37：Timestamp + Sid 防重放机制怎么解释？

Timestamp 用来限制请求有效时间窗口，过期请求拒绝。Sid 或 nonce 用来标识请求唯一性，服务端记录短期已使用 Sid，重复出现就拒绝。两者结合可以防止攻击者截获请求后重复发送。

Q38：Kafka 为什么能提升吞吐？

Kafka 把生产和消费解耦，生产者快速写入 topic，消费者按能力异步处理。它支持分区并行、批量顺序写磁盘、消费者组扩展，所以适合削峰填谷和高并发任务处理。发票系统里引入 Kafka，可以避免请求线程直接执行耗时解析流程。

Q39：Kafka 至少一次、至多一次、恰好一次怎么理解？

至多一次是先提交 offset 再处理，可能丢消息。至少一次是处理成功后提交 offset，失败重试可能重复。恰好一次需要幂等生产者、事务和下游幂等配合，工程成本更高。多数业务选择至少一次 + 幂等消费。

Q40：C++ 项目里你怎么定位线上问题？

可以按“现象 -> 日志 -> 链路 -> 复现 -> 修复 -> 验证”回答。先看错误码、时间点、请求参数和关键日志；再定位是网络、协议解析、业务状态还是外部依赖；必要时构造最小复现；修复后补日志、边界检查和回归测试。简历里提到把排查耗时从 2-3 天压缩到半天，要强调日志字段、链路定位和经验沉淀。

9. 测试 / 工程化 / 行为面

Q41：为什么测试里要 mock LLM 和 DB？

因为单测要稳定、快速、可定位。真实 LLM 有随机性、慢、依赖 API key，数据库状态也可能变化。mock 外部依赖后，单测可以专注验证 deterministic 逻辑，比如 RRF 公式、工具参数校验、agent loop 最大步数、坏 JSON、重复调用拦截等。真实 LLM 行为用 RAGAS 和 agent eval 单独测。

Q42：118 个 pytest 覆盖了什么？

覆盖 chunker、retriever、pipeline、memory、coordinator、tools、tool_registry、tool_policy、mcp_server、mcp_adapter、mcp_production、mcp_audit_api、approvals、tracing、evalops、agent_loop、eval、agent_eval。重点不是数量，而是覆盖了关键失败模式：BM25 cache、RRF 融合、filter fallback、工具参数校验、工具异常、MCP schema 转换/注册、MCP 鉴权/审计/权限策略、人审审批、Agent trace、EvalOps 失败归因、Agent 死循环、max steps、长输出截断、session memory 并发安全等。

Q43：你怎么验证 Claude 或 AI 改的代码是可靠的？

不能只看代码能跑。我的验证方式是：读 diff 确认架构和职责边界；跑 pytest 看 deterministic 逻辑；跑 RAGAS-style 消融看检索质量；跑 agent eval 看工具选择和任务完成；最后整理 technical retrospective，把踩坑和修复记录下来。这样 AI 辅助写代码也能纳入工程验证闭环。

Q44：项目最大的难点是什么？

不是单个 API 调用，而是让 RAG、Agent、MCP 工具接入、人审安全、trace 可观测、评测和工程稳定性统一起来。难点包括：工具粒度怎么拆、模型乱调工具怎么兜底、工具 schema 怎么避免本地和 MCP 双份漂移、高风险动作怎么拦住、评测链路和产品链路怎么一致、reranker/rewrite 是否真的有 ROI、SSE 如何做到真流式、session memory 如何并发安全。

Q45：如果线上 Agent 调错工具，你怎么排查？

先看 metadata 里的 steps，确认实际工具序列和参数。再看工具 schema description 是否误导、用户 query 是否歧义、工具返回是否缺字段、是否有错误回灌。然后复现该 query，必要时加 eval case 防回归。修复可能是改 schema、改 system prompt、补参数校验或增加工具结果字段。

Q46：如果让你部署这个项目，你会怎么做？

后端用 FastAPI + Uvicorn/Gunicorn，前端 Streamlit 单独服务或容器化。ChromaDB 数据卷持久化，配置用环境变量，API key 不进代码仓库。增加日志、超时、重试、健康检查和限流。生产环境还要考虑多进程下 memory 存储不能只放本地内存，可以换 Redis 或数据库。

11. 扩展追问题：基础、部署、C++ 和行为面

Q51：邮件为什么要 chunk？chunk 太大或太小有什么问题？

Embedding 和向量检索通常按片段处理，不能把所有邮件一次塞进去。chunk 太大，主题混杂，检索命中后上下文噪声多；chunk 太小，语义不完整，模型拿不到足够背景。邮件场景一般按正文长度、段落和 metadata 切分，同时保留 email_id、subject、sender、date、chunk_index，方便取完整邮件和排序。

Q52：bge-m3 embedding 的作用是什么？为什么不是直接让 LLM 查？

Embedding 把文本映射成向量，语义相近的文本向量距离更近。LLM 直接查 5000 封邮件成本高、上下文装不下，也不可控。RAG 先用 embedding 检索小范围候选，再让 LLM 基于候选回答，能降低成本、提升可解释性，也能返回 sources。

Q53：为什么用 ChromaDB？生产环境会继续用吗？

ChromaDB 适合本地开发和中小规模 Demo，上手快，能存向量和 metadata，适合验证 RAG 流程。生产环境如果数据量更大、并发更高、需要分布式和权限隔离，可以考虑 Milvus、Qdrant、Elasticsearch dense vector 或云向量库。面试时要说这是阶段性选型，不是所有场景最优。

Q54：cosine similarity 是什么？

cosine similarity 衡量两个向量夹角的余弦值，关注方向相似度而不是长度。文本 embedding 里，方向越接近通常语义越相似。向量检索就是把 query 向量和文档向量比较，找相似度最高的 TopK。

Q55：为什么没有 context recall？

context recall 需要知道标准答案依赖哪些真实上下文，也就是 gold supporting contexts。当前数据集主要是 question-answer 级别，没有精确标注每题应该召回哪些 chunk，所以没有严谨计算 context recall。可以主动承认这是评测局限，后续要补人工标注或构造可追踪数据集。

Q56：faithfulness 低说明什么？怎么优化？

faithfulness 低说明回答可能没有充分依据上下文，存在编造、过度推断或引用错上下文。优化方向包括提高检索质量、让 prompt 要求“只基于上下文回答”、返回来源、对不确定问题拒答、增加 rerank 或 Self-RAG 检查。

Q57：Reranker circuit breaker 是什么？

LLM reranker 可能超时、返回坏 JSON 或分数数量不匹配。如果连续失败，就打开熔断器，暂时跳过 reranker，直接返回原排序，避免每次请求都被同一个组件拖垮。评测不同版本前要 reset circuit breaker，否则某个版本的失败状态会污染后续版本。

Q58：max_tokens 为什么会成为坑？

推理模型可能先输出 reasoning_content，再输出 content。如果 max_tokens 太小，token 在推理阶段耗尽，最终 content 为空，导致 JSON 解析失败或回答为空。所以意图分类、filter extraction、rerank、rewrite 等结构化 LLM 调用都要给足输出预算，并处理 content 为空的兜底。

Q59：reasoning_content 和 content 有什么区别？

一些推理模型会把思考过程放在 reasoning_content，把最终答案放在 content。业务系统通常只应该消费 content，不应该把推理过程直接展示给用户。项目里在结构化输出为空时，会有限地从 reasoning_content 里提取 JSON 作为兜底，但产品回答不直接暴露推理内容。

Q60：Pydantic schema 在 FastAPI 里有什么作用？

Pydantic 用来定义请求和响应模型，负责类型校验、默认值、序列化和 OpenAPI 文档生成。项目里的 AgentRequest、AgentResponse、SearchResult 让 API 输入输出结构清晰，也减少手写参数校验。

Q61：CORS 是什么？为什么 FastAPI 里要加？

CORS 是浏览器的跨域资源共享机制。前端 Streamlit 和后端 FastAPI 可能不在同一个端口，浏览器会限制跨域请求。FastAPI 加 CORSMiddleware 是为了允许前端调用后端 API。生产环境不应随便 allow_origins=["*"]，应该限制可信域名。

Q62：session memory 放内存有什么问题？

内存方案简单，适合本地 Demo，但多进程部署时每个进程都有自己的 memory，用户请求打到不同进程会丢上下文。服务重启也会丢历史。生产环境应该放 Redis、数据库或专门的会话存储，并设置过期时间和容量限制。

Q63：为什么 ConversationMemory 是滑动窗口？

LLM 上下文长度有限，历史越长成本越高，也会引入噪声。滑动窗口只保留最近若干轮对话，能兼顾上下文连续性和 token 成本。项目默认按 user/assistant 成对保留，超过窗口就裁掉最旧消息。

Q64：HTTP 500、400、404 在你的项目里怎么用？

400 通常是客户端参数错误，404 是资源不存在，500 是服务端内部错误。项目里索引文件找不到会返回 404，聊天链路内部异常会记录日志并返回 500。Agent 工具层内部错误不直接变成 HTTP 500，而是返回 tool error 给模型，属于业务级降级。

Q65：多线程、多进程、协程分别适合什么？

协程适合大量 I/O 并发，比如 HTTP、数据库、网络等待。多线程适合阻塞 I/O 或和同步库集成，比如把同步 LLM 流桥接到 SSE。多进程适合 CPU 密集任务，可以绕开 GIL。这个项目主要是 I/O 密集，所以 async + worker 线程更合适。

Q66：队列有没有背压问题？

有。如果 producer 生成速度远快于 consumer，队列无限增长会占内存。当前 token 流速度通常可控，所以使用默认队列问题不大。更严谨的生产方案可以设置 maxsize、超时、取消机制和客户端断连检测，防止慢客户端拖垮服务。

Q67：Dockerfile 和 docker-compose 一般解决什么问题？

Dockerfile 描述应用运行环境，保证依赖一致；docker-compose 用来编排多个服务，比如 API、前端、向量库、Redis。对这个项目来说，容器化可以让面试官或新同事更容易复现环境，也能减少“我机器上能跑”的问题。

Q68：C++ RAII 是什么？

RAII 是 Resource Acquisition Is Initialization，把资源生命周期绑定到对象生命周期。对象构造时获取资源，析构时释放资源。比如文件句柄、锁、socket、内存都可以用 RAII 管理，避免异常路径忘记释放。

Q69：智能指针 shared_ptr 和 unique_ptr 区别？

unique_ptr 独占所有权，不能拷贝，只能移动，开销小，适合明确单一 owner。shared_ptr 共享所有权，用引用计数管理生命周期，适合多个对象共同持有，但有计数开销，也可能形成循环引用，需要 weak_ptr 打破。

Q70：虚函数和多态是什么？

虚函数允许通过基类指针或引用调用派生类实现，这是运行时多态。底层通常通过虚函数表实现。需要注意基类析构函数如果会通过基类指针删除派生类对象，应该声明为 virtual，否则可能只调用基类析构导致资源泄漏。

Q71：select、poll、epoll 有什么区别？

select 有 fd 数量限制，每次都要拷贝 fd 集合，效率较低。poll 用数组解决 fd 限制，但仍然线性扫描。epoll 是 Linux 下更高效的 I/O 多路复用，适合大量连接，事件就绪通知，避免每次全量扫描。

Q72：Kafka 消费重复怎么办？

工程上默认要假设消息可能重复。解决方式是幂等消费，比如用业务唯一键去重、数据库唯一索引、状态机判断、处理成功后再提交 offset。不要只依赖 Kafka 自己保证绝对不重复。

Q73：MySQL 索引为什么能提高查询速度？

索引通常基于 B+ 树，能减少全表扫描，把查询从逐行扫描变成按树路径查找。代价是写入和更新需要维护索引，占用额外空间。设计索引要看查询条件、排序、选择性和联合索引最左前缀。

Q74：事务 ACID 是什么？

Atomicity 原子性，要么全成功要么全失败；Consistency 一致性，事务前后满足约束；Isolation 隔离性，并发事务互不干扰到指定级别；Durability 持久性，提交后即使宕机也不丢。发票、邮箱状态更新、消息处理都可能涉及事务一致性。

Q75：为什么从 C++ 后端转 AI Agent？

可以这样答：我过去做后端和系统工程，比较熟悉接口、并发、稳定性和问题排查。AI 应用不是只写 prompt，也需要后端工程能力把模型能力接入真实系统。所以我选择从 RAG 和 Agent 项目切入，把原来的工程经验迁移到 LLM 应用落地上。

Q76：你最大的短板是什么？

不要说“没有短板”。可以说：我之前主要是后端和系统工程，算法研究和大规模训练不是我的主方向，所以我现在聚焦 AI 应用层，补 RAG、Agent、评测、工程化和模型调用链路。这个回答既诚实，又把短板转成清晰定位。

Q77：如果入职后让你做企业内部知识库，你会怎么设计？

先确认数据源、权限、更新频率和用户场景。架构上做文档清洗、chunk、embedding、向量库、metadata 过滤、混合检索、rerank、生成回答和来源引用。再加权限过滤、评测集、日志观测、反馈闭环和灰度发布。如果任务需要操作系统，还要把能力封装成工具，做 Agent 编排和权限确认。

Q78：如果模型回答错了，你怎么定位是检索错还是生成错？

先看 retrieved contexts。如果上下文没有答案，是检索问题，查 query rewrite、embedding、BM25、filter、rerank。若上下文有答案但回答错，是生成问题，查 prompt、上下文顺序、模型参数、是否需要引用约束或拒答策略。RAG 问题不能只看最终回答，要拆成 retrieve 和 generate 两段排查。

Q79：如果真实用户说“帮我发出去”，Agent 能直接发邮件吗？

当前项目已经新增 send_email 作为 high-risk tool，但它不会直接发送，只会创建 pending approval。人类通过 /agent/approvals/{id}/approve 或 reject 决定是否执行；当前执行结果是 simulated send。生产环境再接企业邮箱 API、权限系统、审计日志、幂等和撤销策略，不能让 LLM 自主执行不可逆操作。

Q80：你觉得这个项目下一步最有价值的优化是什么？

第一是把 MCP 生产化继续加深，从 bearer token/audit 升到 OAuth、租户隔离、TLS 和密钥轮换。第二是把 high-risk human-in-the-loop 从 simulated send 接到真实企业邮箱 API。第三是扩充 agent eval，从 54 条继续扩到 100+ 条，并接入真实失败样本。第四是把 LLM reranker 换成 cross-encoder 或专用 rerank 模型，降低延迟和飘分。第五是把 trace 接成更完整的 observability，看每一步 tool call、耗时、token 和失败原因。

Q81：5000 封邮件都是合成数据，评测结论可信吗？

要分两层答。第一，合成数据不能代表真实企业邮箱的全部分布，所以我不会说评测结论能直接外推到生产。第二，它仍然有价值，因为它能验证系统链路、工具调用、消融对比和失败模式，尤其是同一数据集下 V1-V6 的相对取舍。真正上线前要补真实脱敏数据、人工标注 supporting contexts、多轮多次评测和线上反馈闭环。

加分说法：合成数据适合验证工程闭环，不适合宣称业务泛化。这个边界主动讲出来，比硬说“可信”更稳。
Q82：项目才 2-3 个月，为什么做了这么多？

先承认时间紧凑，然后拆里程碑。底层 RAG、Coordinator、混合检索先跑通；之后新增 function-calling agent loop、工具层、pipeline 统一、agent eval 和 pytest。很多工作不是从零造大系统，而是在一个可运行底座上做架构升级、评测、排错和文档沉淀。GitHub commit history 可以按周验证推进节奏。

11. 前沿 AI 补充：只讲和项目有关的

这部分不是让你堆名词，而是防止面试官问“你了解现在 Agent 方向吗”。答题原则：先落回自己的项目，再说下一步怎么做。

Q84：Function Calling、Tool Calling 和 Agent 是什么关系？

Function Calling / Tool Calling 是模型调用外部函数的协议能力；Agent 是围绕“观察当前状态、选择工具、执行、再判断”的任务循环。你的项目里 /chat/agent 用的是 DeepSeek 原生 function calling 实现轻量 Agent loop；MCP 负责工具如何被标准化发现和执行；human-in-the-loop 负责拦住高风险动作。换句话说，function calling 是 planner 的决策协议，MCP 是工具接入协议，agent loop 是上层控制流程。

Q85：Structured Outputs 和 tool schema 有什么区别？

tool schema 是告诉模型“可以调用哪些工具、每个工具需要哪些参数”。Structured Outputs 更偏“最终输出必须长成某个 JSON 结构”。你的项目里最核心的是 tool schema，因为目标是让模型调用 search_emails、get_email、draft_reply 等工具；评测打分时才更像是在要求模型输出固定 JSON。

Q86：什么是 Agentic RAG？你的项目算吗？

普通 RAG 是“检索 -> 生成”，步骤固定。Agentic RAG 是把检索、取详情、摘要、写回信、申请发信、统计等能力做成工具，让模型根据任务自己决定调用顺序。你的项目可以说是轻量 Agentic RAG：RAG 是底座，/chat/agent 是编排层，MCP-ready backend 是工具接入层，人审和 trace 是工程化保障。不要吹成复杂多智能体协作系统，准确说是“邮件 RAG + function-calling 工具编排 + MCP 标准化工具后端”。

Q87：Agent Eval 为什么比普通 RAGAS 评测多一层？

RAGAS-style 评测主要看检索和生成：答案是否相关、是否忠于上下文、上下文是否有效。Agent eval 还要看模型有没有选对工具、步骤是否合理、有没有撞到最大步数。比如最后答案写得还行，但它没有调用 get_email 就直接编了回信，这在普通答案评分里可能不明显，但在 Agent eval 里应该暴露出来。

Q88：MCP 是什么？和你现在的 function calling 有什么关系？

MCP 可以理解成“把工具、资源、提示词标准化暴露给模型应用的协议”。我的项目现在已经把工具层抽成 tool_registry.py，同一份定义派生本地 function-calling schema 和 FastMCP 注册；mcp_server.py 暴露 6 tools、2 resources、2 prompts，mcp_adapter.py 支持 /chat/agent 切到 MCP backend，并补了 bearer token、schema cache、audit、allowed-tools/read-only policy 和审计查询 API。function calling 决定模型想调什么工具，MCP 决定工具服务怎么被发现和执行。

Q89：GraphRAG 和你项目里的 Self-RAG 是一回事吗？

不是。GraphRAG 通常是把文档抽成实体、关系和社区摘要，用图结构帮助跨文档分析。你的 /chat/graph 是 LangGraph 实现的 Self-RAG 状态机，重点是“检索后自检，不够就 rewrite”。名字里都有 graph，但含义不同：一个偏知识图谱检索，一个偏流程状态图。

Q90：如果面试官问你下一步怎么跟上 Agent 前沿，怎么答？

我会按 ROI 排，不会盲目追新词。第一，把 MCP 生产化继续加深，从 bearer token/audit 升到 OAuth、租户隔离、TLS 和密钥轮换；第二，扩 Agent eval 和 trace，把每次 tool call、耗时、错误原因记录清楚；第三，把当前 simulated human-in-the-loop 接到真实企业邮箱 API；第四，检索侧优先换专用 reranker 或 cross-encoder，而不是继续堆 LLM 调用。
